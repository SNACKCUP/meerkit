# 서비스 화면 위치와 로컬 개발 확인

> 대상: `frontend/src/app/`에 서비스 화면을 만들거나 옮기는 작업, 로컬에서 화면을 확인하는 작업.

- Never: 서비스 화면을 `(sub)` 같은 별도 라우트 그룹이나 `/서비스이름` 하위 경로에 둔다. 서비스 화면은 `src/app/(service)/`에 두고 주소는 루트(`/`, `/projects`)에서 시작한다. (이유: 매무새를 `(sub)/maemusae`에 넣었더니 `/`에 미어킷 웰컴 페이지가 나와, 서비스를 올린 뒤의 실제 모습과 달랐다)
- Always: 서비스를 올린 뒤 `/`는 서비스 첫 화면이어야 한다. 킷 웰컴 페이지(`app/page.tsx`)와 킷 아이콘·og 이미지(`icon.png`, `apple-icon.png`, `favicon.ico`, `opengraph-image.*`)는 서비스 것으로 바꾼다. 같은 이름 파일이 둘이면 라우트가 충돌한다.
- Always: 서비스의 제목·설명 같은 메타데이터는 루트 `app/layout.tsx`에 둔다. `(service)/layout.tsx`는 화면 틀(헤더·푸터)만 맡는다.
- Always: 내 정보 화면은 킷 `MePage`를 `@/meerkit`으로 가져다 쓰고, 서비스 고유 설정은 `extraTabs`로 끼운다. 새로 만들지 않는다. 사용자 메뉴의 "내 정보" 주소는 `meerkitConfig.routes.me`이므로 서비스 화면 주소로 바꾼다. 같은 뜻의 메뉴 항목을 `items`로 하나 더 넣지 않는다.
- Never: `app/(meerkit)`를 통째로 지운다. 비밀번호 재설정, 소셜 로그인 콜백, 약관·개인정보, 관리자 멤버 관리가 여기 있다. 서비스가 직접 만들기 전에는 지우지 않는다.
- Always: 라우트 폴더를 옮기거나 이름을 바꾼 뒤에는 개발 서버를 껐다 켜고 `.next`를 지운다. (이유: 옮긴 뒤 개발 서버가 옛 경로 표를 들고 있어 존재하는 `/login`이 404였다)
- Always: 화면 문구를 고친 직후 하이드레이션 오류가 한 번 보이면, 서버와 브라우저가 서로 다른 시점의 코드를 본 것일 수 있다. 새로고침한 뒤에도 남는지 먼저 확인하고, 남을 때만 코드 문제로 본다. (이유: 푸터 문구를 고치는 중에 "서버 글자와 브라우저 글자가 다르다"는 오류가 났다가 새로고침으로 사라졌다)
- Never: 프로필 이미지가 안 바뀐다는 문제를 화면 코드부터 의심한다. `STORAGE_BACKEND=memory`는 주소가 `https://storage.test/public/...`라 브라우저에서 열리지 않으므로, 이미지를 직접 확인하려면 `s3`(로컬 Supabase나 MinIO)와 `STORAGE_PUBLIC_BASE_URL`을 설정한다. (이유: 업로드는 성공하는데 이미지 주소가 존재하지 않는 호스트였다)
